## 構造の調査と修正

`astro-sight symbols` / `calls` / `refs` で9クレートと Python 補助コードを調べた。
本番の認識経路、CTC、モデルの構造検証と実行、前処理、レイアウト解析、データ出力、
Python の画素変換を確認した。

水平射影の行検出は、列優先で格納した `Array2<u8>` を渡すと
`row.as_slice().unwrap()` がパニックした。先頭と下端に文字行を配置した回帰テストで、
修正前の失敗を確認した。[Issue #2](https://github.com/owayo/ocrus/issues/2) に再現条件を記録した。
連続した行には SIMD、ストライドのある行には画素イテレータを使うよう修正した。

同じ関数で、行数分の集計配列を作成してから行境界を検出していた。集計結果をそのまま
境界検出に渡す構造へ整理し、中間配列をなくした。末尾に背景行の判定を1つ補うことで、
通常の行と画像下端の行を同じ分岐で確定する。行の開始状態も `Option<usize>` にまとめた。
前景数と最小行高のしきい値、上から下への出力順序は維持した。

前景画素数を最後まで数える必要はなく、行の採否に必要なしきい値までで十分なため、
到達後の走査を省く。SIMD の比較結果はビットマスクへ変換し、背景だけのブロックでは
ビット数の計算も省く。[wide の API](https://docs.rs/wide/1.7.1/wide/struct.u8x16.html#method.to_bitmask)
に従い、比較で生成した全ビット0または1のマスクだけを変換する。

単純なビットマスクへの置き換えだけでは、600×800 の予備測定が115.24 µsから
113.17 µsで、95%信頼区間も重なった。この段階では高速化を確認できず、
しきい値による走査の早期終了を加えて再測定した。

CTC のマスク有無による重複、演算 dispatch、文字対応表、モデル変換の分岐も調査した。
今回は、再現したパニックと集計配列・末尾分岐を同時に解消できる行検出を優先した。
CTC の共通化にはマスク長検査と異常入力時の挙動を別途保持する必要があり、今回は見送った。
仕様別の分岐を複雑度だけで分割する変更や、公開 API の削除は行っていない。
未参照と報告された `Quad` や builder の設定は公開 API であり、`run_profiled` は
example の利用を確認したため削除しなかった。

## 性能の測定条件

Windows x86_64、Ryzen 7 5700X（8コア・16スレッド）、Rust 1.99.1 の release、
LTO 有効・codegen-units=1で測定した。両側とも依存更新後の同じツールチェーンと
ロックファイルを使う。比較用バイナリを保存し、前→後、後→前、前→後の順で3組測る。
こちらのビルド、精度評価、Python 検証が終了してから実行した。
両側のプロセスは同じ論理 CPU 14 に割り当て、優先度を AboveNormal、
`RAYON_NUM_THREADS=1` に固定した。推論の数値は単一スレッドの条件であり、
既定の並列実行や過去の保守記録の推論時間と直接比較しない。

CPU の割り当てとスレッド数を固定しなかった初回は、小画像の変更前が174〜402 ns、
W=104の推論が346〜1,428 msと大きく変動したため、採用値には使わなかった。
この初回の生データも JSON の `initial_uncontrolled_measurements` に残した。

各ケースは1秒ウォームアップ後、40サンプルを約3秒かけて収集する。
Criterion の回帰傾きによる1呼び出しの推定時間を使い、3回の中央値と最小〜最大を比較する。
各試行の生サンプルと95%信頼区間も [測定データ](benchmarks/maintenance-2026-10-29.json) に保存する。

```bash
mise exec -- cargo bench --locked --bench preproc -- layout_detect_lines --sample-size 40 --warm-up-time 1 --measurement-time 3 --save-baseline before --noplot
# 同じ条件で変更後も測定する。今回の反復測定では保存した実行ファイルを交互に実行した。
mise exec -- cargo bench --locked --bench preproc -- layout_detect_lines --sample-size 40 --warm-up-time 1 --measurement-time 3 --baseline before --noplot
```

## モデル形式と推論

同じ f16 モデルは42,101,410 bytes（40.2 MiB）。上記の CPU・スレッド条件で、
各実行のロード11回、各幅のウォームアップ2回、ゼロ入力の計測5回を3実行ずつ行った。
ロードは各側33回、推論は各幅・各側15回。計数用アロケータの負荷を両側に含む。

| 指標 | 変更前の中央値（最小〜最大） | 変更後の中央値（最小〜最大） |
| --- | ---: | ---: |
| ロード | 1.349 ms（1.081〜1.872） | 1.272 ms（0.733〜1.596） |
| W=104 推論 | 419.884 ms（399.795〜423.700） | 387.661 ms（256.726〜393.308） |
| W=320 推論 | 878.304 ms（829.990〜891.263） | 873.267 ms（634.407〜887.779） |

出力ハッシュは2つの幅の全試行で前後一致した。変更後の op 合計に対する Conv の割合は
W=104で94.8%、W=320で93.9%だった。推論本体には変更を加えておらず、上の時間差を
行検出の改善効果としては扱わない。既定の並列設定での推論速度の退行は未判定とする。

ロードは1 ms程度で推論に比べ小さく、CBOR 化は見送った。Conv の重み配置変更や int8 化は
演算順序・量子化誤差と検証費用の検討が必要であり、今回の評価条件だけでは採否を判断しない。
行検出の改善には形式変更が不要なため、重み・メタデータ・版番号は変更しなかった。
