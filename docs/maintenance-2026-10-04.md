## レビューと構造の判断

9 クレート、Python バインディング、変換・訓練スクリプトについて、astro-sight の
構造・参照・呼び出し順・差分影響を確認し、入力境界、整数演算、モデル読み込み、
デコード、並列処理、ファイル出力、外部コマンド実行を重点的に調べた。

Claude との設計確認でも、認識処理を `ocrus-engine` に集約する構造は維持する判断とした。
複雑度の高い関数には演算の dispatch や文字対応表が含まれ、数値だけを理由にした
分割は行わなかった。変更した型の利用側は全体のビルドと単体テストで確認した。

## 確認できた不具合と修正

| 場所 | 再現条件・根拠 | 修正 |
| --- | --- | --- |
| 行の正規化 | 矩形の開始座標が画像外だと端の画素を誤って読む。`x + width` がオーバーフローするとパニック | 開始座標を画像寸法までに制限し、終端は `saturating_add` で計算。空領域は既存の余白出力を返す |
| 正規化の幅倍率 | 倍率 0.5 などで出力幅が本体より短くなり、書き込みが範囲外になる | `clamp(content_w, MAX_WIDTH)` で本体の幅を確保して整列 |
| ルビ分離 | `BBox::new(1, 1, u32::MAX, u32::MAX)` の終端計算がオーバーフロー | 両軸の終端を飽和加算して画像内に制限 |
| f16 変換 | `0x0001` は `2^-24` であるべきだが、従来はその半分になる | 非正規化数の指数の初期値を修正。65,536 通りを独立した参照計算と比較 |
| モデルの範囲と形状 | ヘッダの offset + length、巨大な形状の積、負の寸法でパニックまたは不正な範囲計算 | `checked_add` / `checked_mul` と整数変換の検証でモデルエラーを返す |
| モデルの次元式 | 存在しない入力記号を参照すると記号配列の範囲外アクセス。積・和・除算でもオーバーフロー可能 | 記号参照とゼロ除算を読み込み時に検証し、式の演算もチェック |
| reshape | `-2` が推論次元として扱われる。巨大な積や `[-1, 0]` を正しく拒否できない | 推論次元は単一の `-1` のみとし、積とゼロによる推論を検証 |
| ブロードキャスト | `(0, 3)` と `(1, 3)` から `(1, 3)` が作られ、空データを読む | 0 と 1 の組み合わせは空の軸として維持 |
| テンソルの切り出し | 外側の添字が空の `slice_2d(&[])` で `len - 1` がアンダーフロー | 空の添字ではテンソル全体を返す。変更可能な版も同じ対応 |
| 逆順スライス | 最大値の開始位置が軸の長さに制限されて範囲外になる。最小値の終端が 0 に制限され先頭が落ちる | 負の step では開始位置の上限を最後の要素、終端の下限を -1 にする |
| 生画像の入力 | 最大寸法とチャンネル数の積が `usize` を超えるとパニック | 必要バイト数をチェック付き乗算で求め、画像エラーを返す |
| 本番のキャッシュ処理 | 全 lookup が空のキャッシュに対して行われ、insert は全推論の後なので常に未ヒット。各行のテンソルまで余分に複製 | 未ヒットが確定している分岐・ハッシュ計算・中間のテンソル複製を除去し、推論とデコードの順序は維持。独立した `GlyphCache` API は残す |
| JIS マスク | greedy が空の場合、TLA の補助経路は未マスクの出力を読み、禁止クラスを返す | TLA にも同じマスクを適用。通常の greedy 経路では追加の配列を作らない |
| TLA の信頼度 | 同じフレームを2回並べると信頼度が約2になり、0〜1の範囲を超える | 支持の合計による文字選択は維持し、信頼度は有効フレームの平均確率を返す |
| CLI ベンチマーク | `-n 0` が受理され、時間の除算でパニック | clap で 1 以上に制限 |
| 学習データ生成 | 検証比率 2.0 で train 件数の引き算がアンダーフロー。0文字ずつの分割もパニック | 有限の 0〜1 の比率、正の文字数を出力・フォント読み込み前に検証。writer 単体でも検証 |
| Makefile | ルートが `ocrus-bench` のため、`cargo build --release` だけでは CLI が作られない | release は `-p ocrus-cli`、通常ビルド・テストは `--workspace` を指定 |

追加した回帰テストは外部モデルに依存しない。壊れたモデルは匿名 mmap に最小の
メタデータを置いて検証する。Python ではモデルなしの設定検証、配列の次元・非連続配置・
型変換・PIL モード変換のテストも追加した。

macOS の単体配布 Python では `libpython` の探索パスが必要だった。
`make test` は Python 内で探索パスを設定して Cargo を起動するため、シェルや shim が
`DYLD_FALLBACK_LIBRARY_PATH` を除去する環境でも全体のテストを実行できる。

## 検証していない範囲

モデルが未配置のため、実画像の OCR、モデルのゴールデン出力、モデルのサイズ・ロード時間・
推論時間は未検証。モデル形式のバイナリ化や重み配置の変更は実測根拠がなく、今回は行わない。
認識精度が維持されたとは断言できない。

モデルを用意した環境では、まず次を実行する。

```bash
cargo test -p ocrus-engine --release --test smoke -- --nocapture
cargo test -p ocrus-nn --release --test ocnn_golden -- --nocapture
```

長時間の精度測定はユーザー側で実行する。

```bash
cargo test -p ocrus-cli --test char_accuracy char_accuracy_step1 --release -- --ignored --nocapture
cargo test -p ocrus-cli --test char_accuracy char_accuracy_step2 --release -- --ignored --nocapture
```

出力される `logs/char_accuracy_<step>_<epoch>.log` を同じ条件の前回ログと比較する。
このテストは独自経路を使うため、本番エンジンの精度と同一視しない。
