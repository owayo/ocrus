# スクリーンショット・小さい文字の学習と評価

## 今回広げた範囲

- `dataset generate` とフォント描画を使う `dataset from-failures` で、追加のフォントフォルダを指定できる。
- サブフォルダまで TTF / OTF / TTC / OTC を探す。重複する探索先とシンボリックリンクのループを除外する。
- TTC / OTC の各書体をそれぞれ使う。同じファイルのデータは書体間で共有する。
- スタイル分類には各書体のファミリー名を優先する。`sans-serif` はゴシック、`sans mono` は等幅として扱う。
- フォントに収録されていない文字は描画前に除外し、「□」に別の文字の正解ラベルが付くことを防ぐ。
- `--render-heights` で小さい画像に描画し、その解像度のまま学習画像を保存する。

認識精度は未測定。学習データ生成の対象を広げたことが認識にも有効かを判断するには、再学習したモデルをエクスポートして `.ocnn` に変換し、本番パイプラインで既定モデルと比較する必要がある。

## フォントと描画サイズを指定する

```bash
cargo run --release -p ocrus-cli -- dataset generate \
  --output ./training_data/small-text \
  --font-dirs ./fonts/screen \
  --no-system-fonts \
  --font-styles gothic,monospace \
  --categories hiragana,katakana,joyo_kanji,halfwidth_alnum,halfwidth_symbols,fullwidth_alnum,fullwidth_symbols \
  --chars-per-image 15 \
  --samples-per-char 1 \
  --render-heights 12,16,20,24,32,48
```

`--font-dirs` は通常システムフォントへの追加指定で、複数回指定できる。 `--no-system-fonts` を付けると指定したフォルダだけを使う。学習対象を固定する場合はこちらを使う。 存在しない追加フォルダはエラーにする。

`--render-heights` は**描画する画像全体の高さ**を指定する。CSS の `font-size` や文字のインクの高さとは異なるので、画面の表示倍率や Retina 表示によるピクセル数の変化も考慮し、実際のスクリーンショットに含まれる行の高さに合わせて調整する。字形は画像より小さくなる。指定しなければ従来どおり 48px だけを使う。サイズを増やすと画像数も増えるため、最初はフォント数とカテゴリを絞る。

画像は低い解像度で実際に描画し、ノイズ・ぼかしなどの拡張もその解像度で適用する。 モデル入力へのリサイズは学習側で行う。[PaddleOCR公式設定](https://github.com/PaddlePaddle/PaddleOCR/blob/main/configs/rec/PP-OCRv5/PP-OCRv5_server_rec.yml) は学習に複数の入力サイズ、評価に高さ48pxを使う。データ生成側で先に拡大すると、補間が重複して分布が変わるため行わない。 大きく描いた文字にぼかしを加えるだけでは生じない、細い画線の潰れや画素への丸めを含められる。 描画は `ab_glyph` によるもので、OSやブラウザのヒンティング・サブピクセル描画を完全に再現するものではない。 実際のスクリーンショットも評価に含める。

TTC / OTC の先頭書体は従来のファイル名、2番目以降は `ファイル名#1`、`ファイル名#2` として記録する。 異なるファイルで名前が重なる場合は `#file2` などを付ける。探索順はファイルパスで固定する。 同じ内容のフォントを別ファイルとしてコピーした場合の重複は除外しないので、フォルダ内で整理する。 可変フォントから複数の太さを生成する機能はない。太さを変える場合はRegular・Medium・Boldなどの静的フォントを用意する。

## フォント選定の一般的な基準

画面文字を狙うなら、用途に応じてゴシック・UD・等幅と、RegularからBoldまでの太さを選ぶ。
対象言語の文字収録、描画環境、字体の重複を確認し、利用と生成物の取り扱いが許諾されるフォントを使う。
実験ごとの具体的なフォント名・取得元・ライセンス確認・分割条件は、データの管理記録に保存する。
この公開文書では一般的な選定基準とAPIの使い方を説明する。

データの利用・再配布は各フォントのライセンスに従う。フォントを増やす際は画像数だけで判断せず、 `labels.tsv` と `manifest.json` 内のフォント別件数を見て、特定のファミリーだけが多くならないようにする。

## 精度を測る次の段階

単文字評価だけでは、小さいUI文字の実用精度は判断できない。次の条件でテキスト行を評価する。

1. **本番の `OcrEngine` で測る。** CLI・Pythonと同じ認識経路を使い、文字誤り率 `CER = (置換 + 削除 + 挿入) / 正解文字数` と行全体の完全一致率を記録する。
2. **評価フォントを学習から外す。** 太さ違いや等幅・プロポーショナルの派生書体も、同じファミリーとしてまとめて分ける。さらに実際のスクリーンショットを独立した評価集合にする。
3. **サイズごとに集計する。** 極小文字の改善と通常サイズの劣化が、合計値で隠れないようにする。半角・全角や記号を区別した結果を主指標にし、正規化後の結果は補助指標にする。
4. **現実の文章を含める。** 現在のカテゴリ文字列は文字一覧を順に並べたもの。「ファイルを保存する」「検索結果：128件」「v2.4.1」のような自然なUI文字列、英日混在、パス、URL、数字・記号を含む行コーパスの入力を次に追加する。
5. **画面の条件を含める。** 白・暗い背景、文字色、薄い画線、画面倍率、リサイズ、JPEG圧縮、実際のOS描画を評価集合に含める。

現状、Rust側の `val_ratio` は件数の集計であり、評価用の画像を別ファイルに分けてはいない。 Pythonの `finetune` は `labels.tsv` を独自に90/10へランダム分割するので、同じフォント・文字列の 拡張画像が学習と検証の両方へ入る。**この検証値を未知フォントへの精度として扱わない。** フォントファミリーと元画像の単位で分割し、Python側がその分割をそのまま読む対応が必要。

`todo.md` にはファインチューニング後のエクスポートの未解決問題が残っている。 学習結果を既定モデルに置き換える前に、修正・出力検証と `.ocnn` のゴールデン検証を行う。 学習・大規模データ生成・モデル変換は時間がかかるため、ユーザー側で実行する。
