## 構造の調査と修正

`astro-sight symbols` で Rust ソース74ファイルと Python 補助コードの構造を調べ、
エンジンの呼び出し、テンソル演算、モデル検証、CTC、辞書補正、データ出力を確認した。
演算の dispatch、文字対応表、変換器の分岐は、それぞれの仕様に対応しているため、
複雑度だけを根拠に分割していない。認識処理を `ocrus-engine` に置く構造は維持した。

辞書補正には、一致のたびに先頭から文字数を数える処理と、入力全体の `Vec<char>` 化が
あった。一致数が増えると同じ接頭部分を繰り返し走査する。daachorse の一致位置が
UTF-8 のバイト位置であることを確認し、未一致範囲と置換文字列を直接連結する構造にした。
バイト位置を文字位置に変換する補助関数も削除した。最長一致と非再帰の置換仕様は維持した。

テンソル演算では、要素数1の入力がより多くの軸を持つと、その軸が失われる不具合を確認した。
たとえば `[1,1,1]` と `[2]` の減算結果が、本来の `[1,1,2]` ではなく `[2]` になっていた。
共通のブロードキャスト規則で出力形状を決めてからスカラー経路を選ぶよう修正した。
[Issue #1](https://github.com/owayo/ocrus/issues/1) に再現条件を記録した。

修正前に回帰テストが失敗することを確認し、修正後に成功した。両方の引数順、空の軸、
0次元スカラー、減算・除算の順序も確認する。辞書には UTF-8、隣接一致、最長一致、
置換結果を再処理しないこと、長文での拡張を確認する3件のテストを追加した。
辞書テストの一時ファイルは実行ごとに分離し、自動で後片付けする。

変更後の `context` / `impact` / `review --git` では、公開 API の追加・削除・
シグネチャ変更、未対応の呼び出し、不要な公開シンボルは検出されなかった。

## 辞書補正の性能

Windows x86_64、Ryzen 7 5700X（8コア・16スレッド）、Rust 1.99.1 の release、
LTO 有効・codegen-units=1で測定した。両側とも daachorse 5.1.0 を使い、依存更新の影響を
分けて実装だけを比較した。2つの補正ルールと31バイトの日本語・絵文字混在の合成文字列を
使い、1・64・1,024回繰り返した。モデル推論はこのベンチマークに含まない。

```bash
cargo bench --locked --bench dict -- --sample-size 30 --warm-up-time 1 --measurement-time 3 --save-baseline before
cargo bench --locked --bench dict -- --sample-size 30 --warm-up-time 1 --measurement-time 3 --baseline before
```

各ケースは1秒ウォームアップ後、30サンプルを約3秒かけて測定した。
下表は Criterion の回帰傾きによる1呼び出しの推定時間。

| 条件 | 入力バイト | 変更前 | 変更後 | 時間短縮 |
| --- | ---: | ---: | ---: | ---: |
| 2一致 | 31 | 0.266 µs | 0.090 µs | 66.2% |
| 128一致 | 1,984 | 14.560 µs | 4.422 µs | 69.6% |
| 2,048一致 | 31,744 | 2,490.295 µs | 54.435 µs | 97.8% |
| 一致なし | 31 | 0.183 µs | 0.067 µs | 63.2% |
| 一致なし | 1,984 | 5.021 µs | 1.930 µs | 61.6% |
| 一致なし | 31,744 | 103.209 µs | 28.484 µs | 72.4% |

2,048一致の95%信頼区間は、変更前2,417.970〜2,567.093 µs、変更後53.760〜55.088 µs。
6ケースとも短縮し、計測した入力で退行は検出されなかった。
同じ31,744バイト・等長置換で、確保・再確保の要求は3回から1回、累計要求バイト数は
126,988から31,744に減った。これはピーク RSS の測定値ではない。
辞書補正だけの改善であり、OCR 全体が同じ比率で高速になることを示さない。

生のサンプルと推定値は [測定データ](benchmarks/maintenance-2026-10-26.json) に保存した。

## モデル形式と推論

同じ f16 モデルを使い、変更前後の実行ファイルを交互に3回実行した。各実行でロード11回、
各幅で2回ウォームアップ後にゼロ入力5回を計測した。ロードは計33回、推論は各幅15回。
メモリ確保を数えるアロケータを両側に用い、ファイルキャッシュが温まった状態で比較した。

| 指標 | 変更前中央値（最小〜最大） | 変更後中央値（最小〜最大） |
| --- | --- | --- |
| ロード | 0.749 ms（0.705〜0.907） | 0.772 ms（0.716〜1.043） |
| W=104 推論 | 63.370 ms（60.570〜69.242） | 63.214 ms（61.069〜68.418） |
| W=320 推論 | 155.302 ms（143.202〜175.932） | 153.401 ms（145.153〜160.522） |

モデルサイズは42,101,410 bytes（40.2 MiB）。変更後の op 合計に対する Conv の割合は
W=104で85.5%、W=320で82.3%だった。全推論の変動範囲は重なり、速度の変化は
測定のばらつき内と判断した。2つの幅の出力ハッシュは全試行で前後一致した。
ゴールデンは2/2一致した。

ロードは1 ms程度で、今回の修正に形式変更は必要ない。CBOR 化、int8 化、重み配置変更は、
現状のロード負荷と精度・カーネル検証の追加費用を考慮して見送った。Conv が主要な
ボトルネックである傾向は変わらない。重み形式や演算順序の変更は加えていない。

再計測用に `examples/maintenance_profile.rs` を追加した。モデルのパスを渡し、
補正辞書は同じ2ルールを一時ファイルに作成する。

```bash
cargo run --release --locked --example maintenance_profile -- model.ocnn
```
