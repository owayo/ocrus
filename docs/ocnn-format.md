# `.ocnn` モデルフォーマット

`ocrus-nn` が実行するモデルの保存形式。**交換用のフォーマットではなく、コンパイル済みの
実行成果物**として設計してある。入力形式は ONNX、配布・実行形式が `.ocnn`。

## なぜ作り直したか

v1/v2 には、実際に事故を起こした欠陥があった。2026-09-02 に認識精度が 0% まで落ちたとき、
原因は**古い変換器で作られた `.ocnn` が、正常にロードされ、信頼度 0.9 で誤答し続けていた**
ことだった。フォーマットにその状態を検知する術が無く、切り分けに時間が溶けた。

設計を決める前に測った値がこれ。

| 項目 | v2 実測 | 含意 |
| --- | --- | --- |
| モデルロード | 117 µs（mmap） | **ロード速度は最適化の余地なし** |
| 推論（W=104） | 592 ms | ここが本丸 |
| サイズ | 80.5 MB（全 f32） | Conv が 87%、分類器が 10% |
| 壊れた成果物の検知 | 不可能 | 最優先で直すべき欠陥 |

つまりフォーマットの仕事は「読み込みを速くすること」ではなく、**正しさの担保・カーネルが
望む配置・サイズ**の 3 つ。

## ファイル構造

```text
[0, 64)                  ヘッダ（固定 64 バイト）
[meta_offset, +meta_len) メタデータ（JSON, UTF-8）
[data_offset, +data_len) テンソル本体（64 バイト境界）
```

ヘッダ（すべてリトルエンディアン）:

| オフセット | 型 | 内容 |
| --- | --- | --- |
| 0 | `u8[8]` | マジック `"OCNN3\0\0\0"` |
| 8 | `u32` | メジャーバージョン（3） |
| 12 | `u32` | マイナーバージョン |
| 16 | `u64` | メタデータのオフセット |
| 24 | `u64` | メタデータの長さ |
| 32 | `u64` | テンソル本体のオフセット（64B 境界） |
| 40 | `u64` | テンソル本体の長さ |
| 48 | `u32` | メタデータの CRC32 |
| 52 | `u32` | テンソル本体の CRC32 |

### メタデータを JSON にした理由

失敗の実例が「変換が静かに間違っていた」なので、**人間が読めること**に価値がある。
383 ノードで数百 KB、パースは 1〜7 ms。推論が数十〜数百 ms かかる以上、この差は誤差。
バイナリのレコード列にすれば数百 µs 縮むが、Rust と Python の両方で 10 種類のレコードを
手書きパースするコストとバグの危険を負うことになる。割に合わない。

将来ロード時間が問題になったら、CBOR への差し替えは 1 関数で済む。

## メタデータの中身

```json
{
  "converter": "ocrus convert_to_ocnn 1.0",
  "created_utc": "2026-09-02T22:55:00Z",
  "source": { "file": "rec.onnx", "sha256": "26fa4f47…", "opset": 11 },
  "symbols": ["W"],
  "values":  [ { "name": "x", "shape": [{"c":1},{"c":3},{"c":48},{"sym":0}] }, … ],
  "tensors": [ { "name": "conv1.w", "dtype": "f16", "layout": "row",
                 "shape": [64,3,3,3], "offset": 0, "len": 3456, "crc32": 123 }, … ],
  "nodes":   [ { "name": "Conv.0", "op": "conv2d", "stride": [2,2], "pad": [1,1,1,1],
                 "dilation": [1,1], "groups": 1, "act": "relu",
                 "inputs": [{"v":0},{"t":0},{"t":1}], "output": 1 }, … ],
  "inputs":  [0],
  "outputs": [181],
  "golden":  [ { "seed": 12345, "width": 64, "out_shape": [1,8,18385], "argmax": [0,0,…] } ]
}
```

### 1. 名前と型のあるパラメータ

v2 は op のパラメータを無名の `u32[10]` に詰めていた。意味は変換器と実行系の実装に
暗黙に散らばっていて、取り違えても誰も気づけない。v3 では op ごとにフィールドを持つ。

```rust
Op::Conv2d { stride: [usize; 2], pad: [usize; 4], dilation: [usize; 2],
             groups: usize, act: Act }
```

### 2. SSA の値 ID

v2 の「レイヤー番号で参照し、負値なら定数」という規約をやめ、値とテンソルを別の空間に
分けた（`{"v":3}` と `{"t":12}`）。入力の本数制限（v2 は 4 本）も無い。

ロード時に、トポロジカル順・単一代入・参照先の存在をすべて検証する。

### 3. 動的次元を式で持つ

入力幅 `W` を記号として宣言し、そこから派生する次元を `(W * mul + add) / div` の形で持つ。

これにより、**形状計算のためだけに存在していた `Shape` / `Gather` / `Slice` / `Concat` の
サブグラフを変換時に消せる**。v2 ではこれらが実行時に動き、しかも形状の値が f32 テンソルを
通って流れていた（`Reshape` が f32 を整数に読み戻す）。壊れやすく、読みにくい。

変換器は記号推論をしない。**複数の幅で実際に onnxruntime を回して実測し、affine 式に
当てはめる**。当てはまらない次元があれば変換を失敗させる。

### 4. ゴールデン出力

変換時に、決定的な擬似乱数入力（種と幅だけを記録）に対する argmax 列を記録する。
実行側は同じ入力を作って比較できる。これが「このファイルは本当にこう計算するのか」の答え。

```bash
cargo test -p ocrus-nn --release --test v3_golden -- --nocapture
```

壊れた成果物はここで落ちる。ロードのたびには走らせない（1 回の推論ぶん時間がかかる）。

## テンソル

- `dtype`: `f32` / `f16`。**既定は f16** — サイズが半分になり、
  ゴールデンの argmax は f32 と一致し、キャッシュに乗りやすくなるぶん実測で 16% 速い
- `layout`: いまは `row`（行優先）のみ。カーネル向けの事前並べ替え（`conv_k8` など）を
  足す余地を残してある
- 64 バイト境界に配置し、ロード時に検証する。v2 は `*const u8` を `*const f32` に
  キャストしていて、境界の保証が無かった

## 実行系

`crates/ocrus-nn/src/v3/`:

| ファイル | 役割 |
| --- | --- |
| `format.rs` | ヘッダ・メタデータ・検証・テンソルの読み出し |
| `exec.rs` | トポロジカル順の実行、レジスタの生存期間管理、プロファイル |
| `verify.rs` | ゴールデンの再現確認 |

エラーには**ノード番号・ノード名・op 名**が付く。

```text
node 106 (Reshape.3, reshape): reshape to [0, 8, 3, 8, 15] does not match the 2880 elements
```

## 変換

```bash
uv run --with onnx --with onnxruntime --with numpy \
  python scripts/src/ocrus_scripts/convert_to_ocnn.py \
  ~/.ocrus/models/rec.onnx -o ~/.ocrus/models/rec.ocnn --dtype f16
```

変換器がやること:

1. onnxruntime で**全中間値を実測**（形状の当てはめ・定数畳み込み・ゴールデンに使う）
2. 入力が全部定数のノードを実測値に畳む
3. 形状計算のサブグラフを次元式に畳む
4. 融合: BatchNorm → Conv、活性化 → Conv、分解された LayerNorm → 1 op
5. 型付きパラメータと SSA 値 ID で書き出し、ゴールデンを埋め込む

PP-OCRv5 認識モデルでの実績: **383 ノード → 181 ノード**、80.5 MB →（f16 で）40.2 MB。

## 版番号はヘッダに持つ

拡張子は常に `.ocnn`。版番号はヘッダの `version` フィールドにあり、読めない版なら
**「再変換しろ」と言って止まる**。ファイル名に版を出すと、名前と中身が二重管理になる。

**下位互換は持たない。** 旧フォーマット（無名 `u32[10]` の v1/v2）のローダと実行系は
削除済み。古いファイルは変換し直せばよく、読めない実装を抱え続ける理由はない。

## これからも見直すもの

フォーマットは「決めたら終わり」ではない。次の余地が残っている。

| 案 | 見込み | 状況 |
| --- | --- | --- |
| int8（per-channel 対称量子化） | 40MB → 約 21MB | `wide` の int8 内積が弱く、精度検証コストも高い。保留 |
| カーネル向けの事前並べ替え | conv がまだ 8 割 | `layout` フィールドは用意済み、いまは `row` のみ |
| メタデータを CBOR に | ロード 1.2ms → 数百 µs | いま困っていない。困ったら 1 関数の差し替え |
| 重みの重複排除 | 小 | 同一内容のテンソルを 1 つにまとめる |
